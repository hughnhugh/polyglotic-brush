# M0: the three risks, measured

polyglotic-hq project 545, 2026-11-21. Each risk from the plan (520, section
11), what was measured, how to run it again, and what is still to measure.
Numbers are from `brush` built from this repository (Rust 1.100.0, wgpu
30.0.2, the `gnullvm` target), release build.

## 1. The overlay: a transparent canvas above Qt's caption window

**Verdict: it works.** wgpu's DX12 swap chain made from a DirectComposition
visual gives a premultiplied-alpha target on a `WS_EX_NOREDIRECTIONBITMAP`
window owned by a Qt window.

Checked on a private desktop of the main PC (RTX 5070 Ti, 500 Hz), with a Qt
window carrying the caption window's flags (tool, frameless, on top, no
focus, translucent) and the canvas opened **from Python through the C
interface**, as the app will:

| Check | Result |
|---|---|
| Opens through `brush_canvas_create` | yes, in about 180 ms |
| The surface offers premultiplied alpha (`Bgra8Unorm`) | yes |
| Its owner is the captions; it sits above them; DWM doesn't cloak it | yes |
| Input off: a click at the centre reaches the captions, not the canvas | yes |
| Input on: the click reaches the canvas; off again: the captions | yes |
| It never takes activation (`WS_EX_NOACTIVATE`, `MA_NOACTIVATE`) | yes |
| Told the captions' new rectangle, it follows; still above them | yes |
| Another topmost window appears and the captions are raised: canvas, captions, other | yes |
| The captions hide: Windows hides the canvas too | **no** - the host says so (`brush_canvas_set_visible`), then yes |
| Destroy: the window is gone | yes |

Frames, 8 seconds each, a made-up stroke posted at 240 samples a second:

| | Canvas alone | With a 1024 x 1024 simulation, 1 step a frame |
|---|---|---|
| Frame interval, p50 / p95 / p99 / max | 2.00 / 2.18 / 4.07 / 8.13 ms | 2.00 / 2.15 / 3.98 / 8.07 ms |
| Frame work (target to `Present` returning), p50 / p99 | 0.24 / 0.55 ms | 0.26 / 0.57 ms |
| Frames refused by the surface | 0 of 3,876 | 0 of 3,939 |
| DXGI's count: presents over screen refreshes | 3,872 over 3,991 | 3,935 over 3,994 |

So at 500 Hz the canvas misses about 1.5-3 % of refreshes, and a missed
refresh there costs 2 ms.

**Two bugs this found, both fixed here:**
- Opening or closing the canvas from the thread that owns the captions hung
  both threads: Windows sends the owner's thread messages while an owned
  window is made or destroyed. `Overlay::open` and `close` now keep answering
  sent messages while they wait.
- A resize failed inside wgpu (`Surface::configure`): the frame's view still
  held the swap chain's buffer. It is dropped before `Present` now.

**Not checked - it needs eyes on a real screen:** that the ink and the
captions look right together (alpha, no flicker, no black flash on resize),
and anything about a game in full screen underneath. A private desktop is
never shown, and screen capture is not allowed. One 20-second look does it:

```
brush overlay --script --tint 0.14 --seconds 20 --rect 300,300,900,300
```

over the real caption window: a washed rectangle with a black line looping
through it, the captions readable underneath, clicks passing through.

Run the checks again (in a polyglotic-desktop worktree, through the Qt lock):

```
python <hq>/projects/346-claudes-own-validation-loop/tool/qtlock.py --who NNN -- \
  uv run python -m tools.private_desktop run --timeout 100 -- \
  <worktree>\.venv\Scripts\python.exe <hq>/projects/545-the-brush-engine-m0/work/owner545.py BIN_DIR OUT.json
```

## 2. The floor: will the simulation run on slow graphics?

`brush bench`: one whole-canvas flow step, and a step plus the lit picture;
each step its own submission; best of three runs (520's method).

| Adapter | Grid | Flow step | Step + lit picture | Steps in half a 60 Hz frame |
|---|---|---|---|---|
| RTX 5070 Ti, Vulkan | 512 | 0.018 ms | 0.020 ms | 453 |
| | 1024 | 0.034 ms | 0.053 ms | 242 |
| | 2048 | 0.172 ms | 0.282 ms | 48 |
| RTX 5070 Ti, DX12 | 512 | 0.029 ms | 0.030 ms | 285 |
| | 1024 | 0.048 ms | 0.066 ms | 175 |
| | 2048 | 0.184 ms | 0.293 ms | 45 |
| Microsoft Basic Render Driver (the CPU) | 512 | 19.3 ms | 21.5 ms | 0.3 |
| | 1024 | 76.7 ms | 85.7 ms | 0 |
| | 2048 | 328 ms | 365 ms | 0 |

- 520's Python test gave 0.177 and 0.301 ms at 2048 on the same card
  (Vulkan): the Rust engine agrees.
- DX12, which the overlay must use, costs about 4-7 % more than Vulkan at
  2048 and a fixed ~0.01 ms a submission at small grids.
- **A PC with no working GPU driver can't run the simulation** (the CPU
  renderer is roughly 700 to 1,800 times slower than the same PC's card on DX12). Such a PC gets
  pointer ink only.

**Not measured yet:**
- **Real integrated graphics.** `tools/floor-kit/` is the two-minute test:
  copy `brush.exe` and `run-me.cmd` to the PC, double-click `run-me.cmd`,
  send back `brush-floor-report.txt`. It benches every adapter, then draws
  the canvas with the integrated adapter for 18 seconds (alone, with a 512
  simulation, with a 1024 one).
- **The GTX 1080** in the second PC: its card was busy with another job.
  `brush bench --all` there, when it is free.

## 3. Real latency: pen to ink

What software can measure, measured on the private desktop at 500 Hz with
posted samples (their time is when they were posted):

| | p50 | p95 | p99 | max |
|---|---|---|---|---|
| Sample to `Present` returning | 1.37 ms | 2.26 ms | 3.62 ms | 7.35 ms |
| Sample to the sync time DXGI reports for that frame | 5.01 ms | 6.50 ms | 9.58 ms | 15.21 ms |

Read as frames (2 ms each): a sample waits about 0.7 of a frame to be drawn
and presented, then about 1.8 frames until DXGI says it was shown. The
second part is the compositor's frame plus scan-out, which the plan assumed.

**What that predicts at other refresh rates, if the shape holds** (an
estimate, not a measurement): about 2.5 frames from sample to shown - 42 ms
at 60 Hz, 21 ms at 120 Hz - before the pen's own hardware delay and the
panel's response. The plan's gates (35 ms at 60 Hz, 15 ms at 120 Hz) are
"as perceived, with prediction"; M1 has to earn them with two things M0
does not have: starting the frame as late as the GPU time allows (M0 starts
it as soon as the swap chain is free, which is where most of the first 0.7
of a frame goes), and a predicted tail of about one frame.

**Not measured - it needs the person and the pen:**

1. *What the Wacom sends.* `brush pen` opens a washed canvas for 60
   seconds; draw on it. The report says how many samples a second arrived,
   the pressure and tilt ranges, and each sample's time from Windows' own
   stamp for it to `Present`. If the strokes arrive as a mouse (no pressure),
   the report says so: Wacom's driver sends pen messages only with "Use
   Windows Ink" ticked in Wacom Tablet Properties.
2. *The truth.* A 240 frames-a-second phone video of the pen tip and the
   ink, during the same test, drawing fast straight lines. The delay is the
   distance the ink trails the tip, divided by the tip's speed; or count
   frames between the tip crossing a mark and the ink crossing it (4.2 ms a
   frame).
3. *At 60 Hz.* The same again with the display set to 60 Hz (Settings >
   System > Display > Advanced display), or on the laptop.

## What M0 does not do, by design

- The canvas draws every refresh, whether or not anything changed. On a 500
  Hz screen that is 500 frames a second beside a game. M1 draws only when
  the ink changes or the simulation is still moving.
- It keeps every stroke and lays all the ink out again each frame, and
  clears the canvas when a new stroke starts after 4,000 samples.
- The pen's position is whole pixels (`ptPixelLocation`). Windows also gives
  it in himetric units, which is finer: M1.
- Mouse samples are stamped when their message is handled, so their numbers
  flatter the queue. Pen samples carry Windows' own time.
- "Pen only" input (the pen inks, the mouse clicks through) can't be done
  with window styles: a window either takes the pointer or it doesn't. The
  agreed design (a draw toggle, a held key) doesn't need it.
